# AmazonHelp Support Agent — Hiver SDE Intern Take-Home

Brand chosen: **AmazonHelp**. Given a customer tweet, the agent (1) classifies
intent, (2) drafts a reply grounded in how AmazonHelp historically resolves
that intent, and (3) decides auto-handle vs. escalate-to-human with a stated
reason.

## ⚠️ Read this first — data situation

The build environment used to write this code could not reach `kaggle.com`
or `huggingface.co` (network allowlist issue), so it was **not possible to
download the real dataset here**. Everything below is real, runnable code —
but it currently runs against `data/demo_sample.csv`, a **200-row synthetic
stand-in** in the same schema, generated by `data/make_demo_sample.py`. The
golden eval set (`eval/golden_set.csv`) is also built from that synthetic
data. Treat every number in `outputs/eval_report.json` right now as a
**pipeline smoke test, not a real result** — see "What's misleading about my
headline number" below, which is itself the biggest reason.

### Switching to the real dataset
1. Download `twcs.csv` from Kaggle (`thoughtvector/customer-support-on-twitter`).
2. Place it at `data/twcs.csv`. `src/data_loader.py` will automatically prefer
   it over the demo sample (checks for its existence first).
3. Re-mine `RESOLUTION_PLAYBOOK` in `src/reply_generation.py` from real
   resolved threads per intent (currently authored by reading the synthetic
   sample — same process, real inputs).
4. Rebuild `eval/golden_set.csv` by hand-labelling 150-250 **real** examples
   (the assignment requires this be hand-labelled by you, not generated).
5. Re-run everything below — no code changes needed.

## Quickstart (reproduces headline results in <15 min)

```bash
pip install -r requirements.txt

# regenerate the synthetic demo data (already committed, but reproducible)
python3 data/make_demo_sample.py

# run the pipeline over the (demo) dataset
python3 -m src.pipeline --limit 50 --classifier keyword --out outputs/pipeline_results.csv

# run the evaluation harness (baselines + escalation accuracy + judge)
python3 -m src.evaluate

# run unit tests
python3 -m pytest tests/ -q
```

Optional — enable the LLM-based classifier baseline and LLM-as-judge scoring
by setting an API key before running `evaluate.py`:
```bash
export ANTHROPIC_API_KEY=sk-...   # or OPENAI_API_KEY
python3 -m src.evaluate
```
Without a key, `evaluate.py` **skips** the LLM-judge step and says so
explicitly in its output — it never fabricates a score.

## Problem framing — what "good" means here, and what I chose not to build

**Good** for this brand means: (a) the customer's actual issue gets named
correctly, (b) a bot never unilaterally promises money back or a replacement
— those get escalated — and (c) the customer isn't asked to repeat
information the tweet already gave.

**Chose not to build:**
- Full generative (LLM-written, non-templated) replies. Nine intents with
  stable, brand-consistent resolution language is better served by grounded
  templates + slot-fill than free generation, which risks hallucinated
  promises (a refund policy the bot invented). An LLM path exists
  (`llm_backend.py`) but isn't the default.
- Multi-turn thread state tracking (i.e. remembering earlier turns in a long
  thread). The dataset supports it but it roughly doubles scope; single-turn
  classification-of-latest-message was the deliberate cut (see decision log).
- A learned escalation classifier. Escalation is a small, enumerable rule set
  tied directly to intent + a couple of overdue-language regexes — a learned
  model would need far more labelled escalate/don't-escalate examples than
  150-250 to beat the rule set, and would be harder to audit (see decision log #9).

## Results vs. baselines (on the current synthetic golden set — see caveat above)

| Classifier | Accuracy | Macro-F1 |
|---|---|---|
| Trivial (majority class) | 0.255 | 0.045 |
| Keyword rules | 0.873 | 0.873 |
| TF-IDF + Logistic Regression | 1.00 | 1.00 |

Escalation-decision accuracy vs. golden labels: **1.00**.

## What is misleading about my headline number (mandatory section)

The 1.00 TF-IDF accuracy and 1.00 escalation accuracy are **not trustworthy**
and would not survive contact with the real dataset, for a specific reason:
`data/make_demo_sample.py` generates each message from one of 15 fixed
templates, and every template maps deterministically to exactly one intent
and one escalation label. A TF-IDF classifier (or even the keyword rules)
can essentially memorize the vocabulary of 15 templates. Real AmazonHelp
tweets are noisy, sarcastic, multi-issue in one tweet, and the same words
("refund", "broken") appear across intents with different implications
depending on context the templates don't have. On the real dataset I would
expect:
- Keyword-rule accuracy to drop substantially (rules were written by
  eyeballing ~15 template shapes, not thousands of real phrasings).
- TF-IDF to still beat keyword rules but land well under 1.00, probably in
  the 0.6-0.75 macro-F1 range typical for 9-way short-text intent
  classification on noisy social text.
- Escalation accuracy to drop too, since it's currently downstream of a
  perfect intent label — errors compound.
The one number in this repo I'd trust *as a real result* even on synthetic
data is the **relative ordering** trivial < keyword < tfidf, since that
ordering reflects real information gain, not just template memorization.

## Failure analysis — top failure modes (from the synthetic run; real-data equivalents flagged)

1. **Ambiguous multi-word overlap** ("refund" appears in both `return_refund`
   and could plausibly appear in a `complaint_escalation` rant) — keyword
   rules pick whichever regex is listed first. *Real-data version: much
   worse, since real tweets mix intents in one message.*
2. **No handling of sarcasm/negation** — "wow, GREAT service" would hit no
   keyword rule and fall through to `general_inquiry`. Untested here because
   the synthetic templates don't include sarcasm.
3. **Escalation reason is intent-derived, not evidence-derived** — the
   *reason string* cites the intent, but doesn't quote the specific phrase
   in the tweet that triggered it (except the overdue-refund regex). A
   human auditor reviewing escalations would want the trigger phrase
   highlighted.
4. **Reply drafting has no slot-filling** — replies don't insert the
   customer's actual order number even when it's present in the tweet
   (e.g., "#order632084"), which a production version should extract and
   echo back for a more grounded-feeling reply.
5. **TF-IDF classifier needs retraining per brand** — nothing here transfers
   to a second brand; `RESOLUTION_PLAYBOOK` and the keyword rules are
   AmazonHelp-specific and would need to be rebuilt from that brand's own
   historical threads.

## What I'd do next with one more week
- Get the real dataset, re-mine `RESOLUTION_PLAYBOOK` from actual resolved
  AmazonHelp threads (cluster replies per intent, extract common structure).
- Hand-label a real 150-250 example golden set myself, stratified across
  intents so rare ones (e.g. `account_login`) aren't underrepresented.
- Add slot extraction (order number, product name) via regex + a small NER
  pass, and use it in both reply drafting and escalation reasons.
- Wire the LLM-as-judge for real with `ANTHROPIC_API_KEY`, and hand-score
  ~40 replies myself to get a real judge-vs-human agreement number (the
  mechanism is built in `evaluate.py` / `eval/human_judge_sample.csv`, just
  not exercised with a live key in this environment).
- Try a confidence threshold on the TF-IDF classifier so low-confidence
  predictions escalate to human review regardless of intent, instead of
  trusting a possibly-wrong intent label all the way through.
